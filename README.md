# Spacepeek

[Project page](https://phena109.github.io/spacepeek)

Space-bar file preview for Windows Explorer and the Windows desktop. Select a file, press Space, and a single topmost window shows a bounded text preview. The preview does not take focus from Explorer or the desktop. While it is open, the preview follows the selection in that Explorer window or on the desktop: the arrow keys, or a click on another file. Press Space or Esc again to close it. The header has an × button as well. PNG, JPEG, BMP, GIF (first frame), ICO, and WebP are previewed too: the format is sniffed from the magic bytes, and the file has to fit the size limits. Files named `.svg` or `.svgz` (any case) are drawn as a still picture. The SVG is parsed and rasterised on the loader thread, then shown in the same image view as a PNG, so fit, zoom (wheel, `+`/`−`, `0`, `1`), pan, and double-click-to-open work unchanged. The header details end with `SVG`. Actual size (`1`) is the SVG's intrinsic size at the monitor DPI. The bitmap is rendered at the current window body size (capped); zooming in scales that bitmap. An SVG that is too large, too nested, too complex, or not valid XML uses the unsupported-file view (quick info and the shell icon) with a short reason. Text, HTML, raster, and Markdown files pay no SVG work. Files named `.md` or `.markdown` (any case) that pass the text sniff are formatted as Markdown: headings, emphasis, lists, quotes, code, links as underlined text, and rules. That layout is built on the loader thread and shown in a RichEdit control loaded only the first time a Markdown file is previewed. Links are not clickable. Images in the file become `[image: alt]` (or `[image]` when there is no alt); nothing is fetched. Raw HTML is shown as literal monospace text. Tables are aligned monospace rows. If the decoded source is more than 64 KiB or more than 2,000 lines, the preview stays plain text and the header says `Markdown as text`. A larger file that still fits those caps after the bounded read is formatted, with the usual truncation notice. The header for a formatted file ends with `Markdown`. Files named `.html` or `.htm` (any case) stay on that plain-text path. The source is shown in the same monospace EDIT control, tags included, with the same 64 KiB and 2,000 line caps, the same sniff, and the same truncation notice. The header details end with `HTML source`. Nothing is rendered, scripts do not run, and nothing is fetched. `.htmlx` and `.xhtml` stay ordinary text when the bytes look like text, without that label. An `.html` or `.htm` file that fails the text sniff uses the unsupported-file view. Markdown, PDF, SVG, and raster files do no HTML work. Files named `.pdf` (any case) show the first page in that same image view. The window and the shell icon appear immediately, the same way an unsupported file does, and the rendered page replaces the icon when it is ready. While the page is still rendering the header says `PDF`. Once it is up the details look like `12 KB · 612 × 792 · 12 pages · PDF` (`1 page` when there is one). Those dimensions are the page size in DIPs, which is the page in pixels at 96 DPI. Actual size (`1`) is that page size at the monitor DPI. The bitmap is rendered once, fitted into the current window body, and a smaller page is not scaled up. Zooming in scales that bitmap. Dragging the border does not render the page again. A password-protected, damaged, too-large, or too-slow PDF keeps the shell icon and a short reason. Text, HTML, raster, Markdown, and SVG files do no PDF work. An extensionless file whose first bytes are `%PDF` takes this path. A named `.txt`, `.html`, `.htm`, `.png`, or `.svg` does not, even when the bytes start that way. A file named `.pdf` takes the PDF path even when the bytes are not a PDF. An empty `.pdf` stays the empty-file message.

With a picture showing, the mouse wheel zooms in and out around the pointer. `+` and `−` do the same, including the numeric keypad. `0` fits the picture to the window. `1` shows it at actual size: one image pixel is one pixel at 96 DPI, scaled with the monitor the same way the fitted picture is. Those keys are taken only while a picture is showing, so a text preview still scrolls on the wheel and Explorer can still use `0` and `1` for type-ahead. Zoom stays between 10% and 800% of the fit-to-window size, in steps of one quarter, and the file is not decoded again. Drag the picture to pan when it is zoomed past that fit size. The header still moves the window. The × button still closes the preview. A drag on the picture at the fit size does not move the window or the picture. Arrow keys still change the selected file. A double-click that does not move the picture still opens the file. A drag that pans it does not also open it.

Text is drawn in a monospace font (Cascadia Mono, then Consolas) with word wrap off and a horizontal scrollbar, so columns and indentation stay aligned. Each line sent to the preview is capped at 1,000 UTF-16 code units. A cut line adds a … marker (one more unit). That stays under 1,024 units, which is where the edit control would otherwise split one source line into a second row. The preview loads at most the first 64 KiB. When that is not the whole file, or when lines were shortened, a notice at the top of the text says what is shown (for example `Showing the first 64 KB of 1.2 MB`). When the two sizes would round to the same text, the notice uses exact byte counts instead, such as `Showing the first 65,536 of 65,537 bytes`. The header repeats that state in short form, such as `12 KB · 2,000 lines (truncated)`.

A slim header shows the file name and that details line. Drag the header to move the window. Drag an edge or a corner to resize around the window's centre, which stays fixed. A corner grows or shrinks all four sides (left matches right, top matches bottom). The left or right edge changes the width on both sides and leaves the height alone. The top or bottom edge changes the height on both sides and leaves the width alone. The smallest size is 320×200 logical pixels. If a side would cross the monitor work area, the window shrinks, still centred, until it fits. If the minimum size cannot stay centred inside that work area, the window shifts just enough to stay inside. When the work area itself is smaller than the minimum on that axis, the window uses the work-area span. The last size you set is reused for the next preview of every kind (text, image, Markdown, or a message) until Spacepeek exits. Nothing is written to disk. The size is stored in logical pixels and scaled for the monitor's DPI. Error and empty-file windows start smaller (480×320 logical) until you resize. Image and Markdown previews use the same default as text until then. A PDF uses that image default as well, including the icon shown while the first page is rendering and a PDF that failed to open, so the page can replace the icon without a size jump. A size you already set is shared with every other kind. The extra height fits a short message plus type, size, and modified time. An unsupported file also shows that file's Explorer shell icon above those lines once the icon is ready. The × button picks up a light grey background while the pointer is over it. Double-click the text or the picture to close the preview and open that file with its usual app. A folder opens too. A double-click on the header or the × button does not.

## Download

- Nightly builds are published as a rolling pre-release at [Nightly release](https://github.com/phena109/spacepeek/releases/tag/nightly).
- A new nightly is built about 2am Sydney time only on days when main changed.
- Each nightly has two files, `spacepeek-<version>-x64.exe` for Intel and AMD PCs and `spacepeek-<version>-arm64.exe` for Arm PCs (Snapdragon, or a Windows VM on Apple silicon), plus `SHA256SUMS.txt`.
- Check the version with `spacepeek.exe --version` (looks like `0.0.1-nightly.YYYYMMDD+commit`).
- Builds are unsigned, so Windows SmartScreen may warn on first run (More info, then Run anyway) and Smart App Control may block them.
- Nightlies are untested previews, not releases.

## Status

First runnable vertical slice.

The preview core (bounded reads, character-boundary truncation to 1,000 UTF-16 code units per line, binary sniffing, a deny-list of known binary extensions, cancellation, state machine, keyboard rules, which Explorer or desktop selection events and clicks schedule a reload, header text, hit testing, close-button hover, which double-click region opens the file, quick-info lines for unsupported files, remembered window size (shared by text, image, Markdown, and message previews, in logical pixels), center-anchored resize of the eight edges and corners, the minimum-size and work-area clamps, odd-pixel centre stability, the sentences shown for errors and empty files, image zoom and pan placement, which zoom keys are taken, the icon file's directory, which pixel size a DPI selects, whether an unsupported preview should request a shell icon, that icon's DPI size and layout above the message text, generation-staleness and timeout acceptance, whether a cached icon already matches a request, whether the first-run tray balloon should show, HTML extension detection (`.html` and `.htm` only, any case, not `.htmlx` or `.xhtml`) and the `HTML source` header, Markdown extension detection, the Markdown render model, RTF escaping, the huge-file Markdown fallback, SVG path detection, SVG caps (file size, svgz inflate, node count, nesting depth, output pixels, embedded-image pixels, parse budget), SVG output-size clamping, SVG image-href blocking, PDF path detection (`.pdf` in any case, not `.pdfx`; an extensionless `%PDF` prefix only), PDF caps (128 MiB, 32 million pixels, 4096 on a side, 1.5 s), PDF fit and DPI math, PDF header text (`1 page` or `N pages`), PDF failure sentences, the icon-then-page session (a matching generation replaces the icon, a stale generation is dropped, and Esc or a new file does not show a late bitmap), and classifying Explorer vs desktop vs other window classes, including whether an empty desktop selection passes Space) is implemented and unit-tested. The Windows runtime is wired: single-instance mutex, low-level keyboard hook, Explorer and desktop selection lookup, and one non-activating `SpacepeekPreview` window. Every UI transition goes through `state::step`. Markdown uses a RichEdit control (`Msftedit.dll`, class `RICHEDIT50W`) filled from RTF generated on the loader thread. The DLL is loaded only when a Markdown preview is first shown. The existing EDIT text path and the raster image path are unchanged when the file is not Markdown, SVG, or PDF. An `.html` or `.htm` file uses that EDIT path; the only addition is the `HTML source` header label. That label is unit-tested. It has not been run on a Windows desktop. SVG is rasterised on the loader thread into the existing image view. PDF work starts only after a file has been classified as a PDF. The first page is rendered on a dedicated worker (`spacepeek-pdf`) that initialises its own WinRT apartment the first time a PDF is previewed, not at process start and not on the UI thread. The window is already showing the shell icon by then. That path is compile-checked and CI-tested; it has not been run on a Windows desktop. Desktop Space is classified from window class names (`Progman` or `WorkerW`, `SHELLDLL_DefView`, `SysListView32` titled `FolderView`). The desktop folder is resolved only in that case, through `IShellWindows::FindWindowSW(CSIDL_DESKTOP)`. When that list is focused, a selection count of 0 passes Space through. A count of one or more, or a count the hook could not read within 30 ms, still takes Space. Explorer is not sent `LVM_GETSELECTEDCOUNT`. The Explorer HWND walk is unchanged when Explorer is the origin.

Compile-checked for the Windows targets below on a Linux host. **Never executed on Windows.** No timings are claimed for this build. The PDF open times under Limitations are from an earlier ARM64 VM spike, not from this preview path.

## Supported platform

Windows 11 only, x86_64 and aarch64. There is no compatibility code for older Windows versions.

## Build

On Windows 11:

```bash
cargo build --release
```

From Linux, cross-check the Windows targets (this does not produce a machine that has been run):

```bash
cargo check --target x86_64-pc-windows-gnu
cargo check --target aarch64-pc-windows-msvc
```

## Run

Start `spacepeek.exe` and leave it running. Spacepeek does not start automatically with Windows. To start it when you sign in, put a shortcut in the Startup folder (`shell:startup`).

Spacepeek's own icon stays in the notification area while it is running. The same mark is the program icon in Explorer and on the preview window. It is embedded from `assets/spacepeek.ico` (resource id 1). A thin white hairline sits outside the page stroke in that file, so the dark outline still separates from a dark taskbar. The hairline is part of the icon asset. It is not drawn while a preview runs. It has not been looked at on a Windows desktop. The version resource sets CompanyName to Spacepeek. The notification area and the caption use the small size, 16 pixels at 96 DPI, and the window uses the large size, 32 pixels at 96 DPI. Both scale with the monitor (20 and 40 at 125%, 24 and 48 at 150%). Right-click that icon and choose Exit Spacepeek to quit. A left-click opens the same menu. Or run `spacepeek.exe --quit`. That exits with code 0 when it finds the running instance, and with code 1 when nothing is running. If nothing is running, `--quit` shows a short notice. `spacepeek.exe --version` prints the build version.

The first time Spacepeek starts for a Windows user, that icon shows an info balloon: "Spacepeek is running. Select a file in Explorer and press Space. Right-click this icon to quit." The title is "Spacepeek". After that call succeeds, Spacepeek stores one DWORD, `FirstRunBalloonShown` = 1, under `HKCU\Software\Spacepeek`. Later launches stay quiet. Restarting Explorer puts the icon back and does not show the balloon again. If the call fails, the value is left unset so the next launch can try again. The icon may land in the hidden notification overflow. Windows does not let an application move its own icon out of that overflow. The balloon text, the UTF-16 limits, the value name, and the already-shown check are unit-tested. The Win32 calls are compile-checked, not run on a Windows desktop.

A second launch shows a message that Spacepeek is already running and exits with a non-zero code.

On Linux and macOS the binary prints `Spacepeek runs on Windows only` and exits with code 1.

1. Build and start `spacepeek.exe`. The notification area shows the Spacepeek icon, and Explorer shows that same mark on `spacepeek.exe`. Neither is the generic Windows application icon.
2. Open File Explorer and select a text file. The extension does not decide this for ordinary text: `.txt`, source code, `Makefile`, `Dockerfile`, `LICENSE`, and `.gitignore` all preview when the bytes look like text. A `.md` or `.markdown` file that looks like text is formatted instead; a `.mdx` file stays plain text. A `.html` or `.htm` file that looks like text shows the source, tags included, in that same monospace preview, and the header details end with `HTML source`. A `.xhtml` or `.htmlx` file stays plain text without that label. A long `.html` file shows the same truncation notice as other text. An `.html` or `.htm` file whose first 8 KB contains a NUL or invalid UTF-8 shows the unsupported-file view. This HTML labelling is compile-checked and CI-tested; it has not been run on a Windows desktop. Selecting a file on the desktop and pressing Space is meant to open the same preview, anchored on the monitor under the cursor. That desktop path is compile-checked and CI-tested; it has not been run on a Windows desktop.
3. Press Space. A preview window should open over that Explorer window with the file name in the header and the file text in a monospace font. A Markdown file shows formatted text and `Markdown` in the header details. An `.html` or `.htm` file shows source text and `HTML source` in the header details. Explorer keeps the keyboard focus, and the preview text has no caret. Drag the header to move the window. Drag an edge or a corner to resize around the centre: a side changes only that dimension, a corner changes all four sides, and the window stays inside the monitor work area. Click × to close it. Moving the pointer over × turns that button a light grey; moving it away clears the grey. Double-click the text or the picture (not the header, and not ×) to close the preview and open the file the way Explorer would. A folder opens in Explorer. A triple-click does not open it twice. A long file shows a truncation notice at the top of the text and `(truncated)` in the header. A Markdown file whose decoded source is over 64 KiB or 2,000 lines stays plain text and the header says `Markdown as text`. Clicking or dragging the header should not leave a caret in the preview or take the keyboard away from Explorer for good.
4. Press Space or Esc. The window closes. Explorer still has the focus. Press Space again. The preview opens without clicking the file list first.
5. Press F2 to rename, then type a space. The space is inserted into the rename edit.
6. Click the address bar and press Space. The space is typed there.
7. In the file list, type the start of a name and, within about a second, press Space. The space continues Explorer's type-ahead search instead of opening a preview.
8. With a preview open, press Down or Up. Explorer moves the selection and the preview follows the new file. Clicking a different file in that same Explorer window does the same. Left and Right do the same when Explorer changes the selected file. Page Up, Page Down, Home, and End scroll the preview text. The mouse wheel over a text preview and the scrollbars also scroll it. A long line scrolls sideways on the horizontal scrollbar. A click on the preview itself, including the header and ×, leaves the shown file in place.
9. Select a PNG, JPEG, BMP, GIF, ICO, WebP, or SVG (`.svg` / `.svgz`) and press Space. The window shows the picture. An SVG uses the same zoom and pan controls as a PNG. The picture scales at once; after the zoom has been still for a moment it is drawn again at the on-screen size, up to 32 million pixels. The header ends with `SVG`. A huge or broken SVG shows the unsupported-file message with a short reason, plus type, size, modified time, and the shell icon. Select a `.pdf` (any case) and press Space. The window opens at once, at the image size, with the shell icon, quick info, and `PDF` in the header. The first page then replaces the icon in the picture view. Fit, zoom, pan, and double-click-to-open work as for a PNG. `1` is the page at the monitor DPI. The header then includes the page count, such as `12 KB · 612 × 792 · 12 pages · PDF`. A password-protected PDF keeps the icon and says the PDF is password protected. A damaged PDF says it looks damaged or isn't a valid PDF. A PDF over 128 MiB says it is too large. This path is compile-checked and CI-tested; it has not been run on a Windows desktop. The wheel zooms that picture around the pointer. `+` and `−` zoom as well, including the numeric keypad. `0` fits it to the window. `1` jumps to actual size. Drag the picture when it is zoomed past the fit size to pan it. Dragging the header still moves the window, × still closes it, and dragging the picture when it already fits does nothing. Arrow keys still move to the next file. A double-click that does not move the picture still opens it. A drag that pans it does not. GIF shows the first frame only, and so does an animated WebP. An ICO with several sizes shows the largest one that fits. A PNG renamed to `.txt` still previews, because the type comes from the magic bytes. Select a known binary file (for example `.exe`, `.zip`, `.dll`) and press Space. The window shows a short message such as `notes.zip can't be previewed — this file type isn't supported yet`, and under that, when the facts can be read without opening the file, lines for Type (the Windows type name, or the extension in capitals plus `file`), Size (such as `1.2 MB (1,234,567 bytes)`), and Modified (local date and time). The file's Explorer shell icon is drawn above those lines once it is ready: 96 logical pixels, scaled with the monitor, fetched after the window is shown and only for that unsupported outcome. The fetch runs once for that file and pixel size; the same file is not fetched again while that icon is showing, including when Explorer reports the same selection again. The message text is laid out the same way as before, so the late icon does not move it; a lookup that fails or takes more than a second leaves the text as it is. A text extension whose first 8 KB contains a NUL or invalid UTF-8 shows `<name> doesn't look like text` and the same kind of lines and icon. Access denied, a missing file, and a file that is open in another program stay a single sentence. An empty file shows `This file is empty`. A folder shows `Folder: <name>` and, when the entries can be listed, a count capped at `10,000+`. A `.lnk` shortcut shows `Shortcut to <target>` when the stored target can be read, and otherwise says that previewing shortcuts isn't supported yet. A file locked by another program says it is open in another program and can't be read. A file that was deleted says it no longer exists. A file you cannot access says access was denied.
10. Press Space on a slow file and press Esc before the window appears, or switch to another app. The preview should not appear. With a preview open, activate another app. The preview closes.

If nothing is selected in Explorer, or the selection has no filesystem path, Space does not open a window. The hook cannot query Explorer's list, so the key was already taken; the UI thread checks the selection and then does nothing. Putting the key back would enter the hook again. On the desktop the icon list is a real `SysListView32`. When that list is focused, the hook reads `LVM_GETSELECTEDCOUNT` with `SendMessageTimeoutW` (`SMTO_ABORTIFHUNG | SMTO_BLOCK`, 30 ms) and does not send that message for Explorer. A count of 0 passes Space through to the desktop. A count of 1 or more takes Space as before. If the call times out or fails, Space is still taken. A rename Edit, type-ahead, the taskbar, and Progman without the icon list focused leave Space alone.

## Limitations

- No process isolation or sandbox. Parsing runs in-process. The mitigations are a bounded read, a deny-list of known binary extensions, binary sniffing, and never executing the file.
- Space is intercepted with a global low-level keyboard hook.
- Only the first selected item is previewed.
- Files are text when the first 8 KB has no NUL and is valid UTF-8 (a partial character at that 8 KB edge is allowed), or when the file starts with a UTF-16 BOM. `.html` and `.htm` (any case) take this text path when that sniff passes. The preview is the source, tags included, in the existing EDIT control, with the same 64 KiB and 2,000 line caps and the same truncation notice. The header details end with `HTML source`. There is no HTML renderer, no WebView, and no network. `.htmlx` and `.xhtml` are not labelled `HTML source`. A sniff failure uses the unsupported-file view, the same as any other non-text file. Markdown, PDF, SVG, and raster loads do not pay for this label. The detection, caps, and header wording are unit-tested. This labelling has not been run on a Windows desktop. PNG, JPEG, BMP, GIF (first frame only), ICO, and WebP are previewed (magic-byte sniffed, with size limits); the extension is ignored. `.svg` and `.svgz` (any case) are previewed as a still image after that sniff: a PNG renamed `.svg` still uses the raster path. An extensionless file whose first bytes look like `<svg` or `<?xml` plus `<svg` (or gzip) also takes the SVG path. SVG input is capped at 8 MiB (16 MiB decompressed for `.svgz`, enforced while inflating). After parse, more than 200,000 nodes, nesting deeper than 256, a parse longer than 1.5 s, or a zero/NaN size uses the unsupported-file view. The pixmap is capped at 32 million pixels and the existing image display box (4096 on a side). External `href` / `xlink:href` (file, http, relative path) are not loaded for `<image>`, `<use>`, or `<feImage>`, and neither is nested `data:image/svg+xml`. `data:` PNG/JPEG/GIF/WebP are, when the header reads as at most 16 million pixels and the document stays within 64 million; a header that cannot be read is dropped. Gzip (a `.svgz`, or a `.svg` whose bytes are gzip) is inflated once, up to 16 MiB, and a second gzip layer is rejected before usvg sees the text. `<script>` and SMIL are ignored (static resvg). System fonts load once, on the worker, and only for an SVG that contains text. A settled zoom reuses that same cache. Wheel and keyboard zoom scale the bitmap already on screen, so the picture moves immediately. After zoom, fit, or actual size has stayed still for 120 ms, and only while the pointer is not panning or dragging the border, a background thread named `spacepeek-svgzoom` re-reads the file and rasterises at the on-screen pixel size. That thread starts on the first such request, not at process launch, and not for a text, raster, Markdown, PDF, or HTML preview. The target is the fitted picture times the zoom, at the monitor DPI. Fit is that destination at 100%. Actual size is the intrinsic size at the monitor DPI. A bitmap that is already that size is not rendered again. Past 32 million pixels the target is scaled down, and further zoom keeps scaling that capped bitmap instead of allocating a larger one. A newer target supersedes an older one. resvg cannot stop mid-render, so a finished bitmap whose sequence, file, or size no longer matches is dropped. The previous SVG bitmap is replaced. Esc, a new file, or a new target clears the wanted sequence. The loader still spawns one thread per file; the first fit raster and a zoom raster share one parse+render slot (a render that has already started cannot be interrupted). That path is compile-checked and CI-tested; it has not been run on a Windows desktop. A file named `.pdf` (any case) previews page 1 through `Windows.Data.Pdf` into the same image view. The window and the shell icon are up before that work. One thread, `spacepeek-pdf`, starts the first time a PDF is previewed and calls `RoInitialize(RO_INIT_MULTITHREADED)` on that thread only. It is not started at process launch and it does not run on the UI thread. At most one render is in flight; a newer file replaces the request. Esc, a new selection, or a closed window cancels the operation and drops a late bitmap. Open plus the first-page render is capped at 1.5 s; past that the icon stays and the message says the PDF took too long to open. The file cap is 128 MiB, a safety cap rather than a measured failure. The rendered page is capped at 32 million pixels and 4096 pixels on a side, fitted to the window body at the monitor DPI, and a smaller page is not scaled up. A zero, negative, or non-finite page size keeps the icon. A password-protected or damaged file keeps the icon. There is no password prompt. After the pixels and the page count are copied, the WinRT document, page, and streams are released. There is no process-wide PDF cache. Text, HTML, raster, Markdown, and SVG loads do not start this thread. An extensionless file that starts with `%PDF` uses this path. A named non-PDF extension is not sniffed for that prefix. This path is compile-checked and CI-tested; it has not been run on a Windows desktop. An earlier measurement spike on a Windows 11 ARM64 VM (native ARM64, first page at preview size, separate from this preview path) recorded about 19 ms warm and about 217 ms process-cold for a small text page, about 22 ms and about 78 ms for a 320-page text book, about 114 ms and about 196 ms for a vector-heavy drawing, about 175 ms and about 328 ms for a large scanned image, and about 20 ms for a broken or password-protected file. Working set in that spike went from about 46 MB for plain text up to about 120 MB for the heavy files. Cancelling the async operation in that spike returned immediately on the heavy files, both while opening and while rendering. Page count did not change first-page time there. The first PDF after process start paid an extra about 150–200 ms to load Windows' PDF engine. Those figures are not timings of this build. Known binary extensions are refused before that sniff and reported in a sentence that includes the file name. That sentence, and the "doesn't look like text" sentence, can include type, size, and modified time gathered without reading the file contents. The Windows type name comes from `SHGetFileInfoW` with `SHGFI_TYPENAME | SHGFI_USEFILEATTRIBUTES`, or the extension in capitals plus `file` when the shell name is unavailable. Those shell calls are compile-checked, not run on a desktop. The same unsupported preview also asks for the file's Explorer shell icon through `IShellItemImageFactory::GetImage` with `SIIGBF_ICONONLY` (no thumbnail extraction), after the window is shown, on a worker that initialises its own COM apartment. A lookup that fails or takes more than a second leaves the text as it is. The same file and pixel size is not fetched again once that lookup has finished. That path is compile-checked, not run on a Windows desktop. A `.lnk` file is not opened as text; the Windows build reads the shortcut's stored target for the message and does not search or show a link dialog. A zero-byte file is an empty-file message, not a blank preview. A folder is not listed as text; the message names the folder and, when listing succeeds, how many entries it has, stopping at 10,000.
- The preview keeps at most 2,000 lines and 1,000 UTF-16 code units of each line. Cuts are on a character boundary, so a surrogate pair is not split. The notice at the top reports the bytes shown and the file size, and says when lines were left out or shortened. When the rounded sizes would read the same, it prints exact byte counts.
- Markdown preview is CommonMark plus strikethrough and tables, parsed with `pulldown-cmark` (no HTML renderer, no getopts). There is no WebView and no network. Raw HTML inside a Markdown file is literal text. A file named `.html` or `.htm` is not parsed as Markdown. Images in the document are not loaded. Tables are monospace aligned rows. The parse and the RTF run on the loader thread. The RichEdit control, `Msftedit.dll`, RTF streaming, scrolling, and DPI for that path are compile-checked, not run on a Windows desktop.
- Arrow keys are delivered to Explorer while that window still has focus. The preview reloads only when the selected path changes. In Details view, Left and Right often leave the same file selected. While the preview is open, a click on another file in that Explorer window reloads the same way. Spacepeek waits for Explorer to apply the click, then reads the selection again. A click on the preview window leaves the shown file in place. A click that clears the selection leaves the current preview in place. Arrow keys are not forwarded when the preview window itself is in the foreground.
- A Space that continues an Explorer type-ahead search is passed through. While a preview is already open, that Space does not move the preview.
- Image zoom runs from 10% to 800% of the fit-to-window size, in 25% steps. For PNG, JPEG, BMP, GIF, ICO, WebP, and PDF, the decoded bitmap is reused; only the destination rectangle changes. An SVG uses that same rectangle immediately, so pan stays on the bitmap already shown. Actual size is still the intrinsic SVG size at the monitor DPI. Once zoom, fit, or actual size has been still for 120 ms, the SVG is rasterised again at the destination size on `spacepeek-svgzoom`, capped at 32 million pixels. The new bitmap replaces the old one, and it is not swapped in while the pointer is panning or the border is dragging. A PDF is not rendered again on zoom: actual size is the page size in DIPs at the monitor DPI. A border drag does not start a new PDF render. A resize while dragging the border uses that same rectangle: fit stays fitted, and a manual zoom keeps its scale. The PDF and raster files are not decoded again. Wheel zoom, keyboard zoom, drag-to-pan, the centre-anchored border drag, and the SVG settle rules are compile-checked and covered by unit tests. They have not been run on a Windows desktop.
- The Windows runtime has not been executed. Compile checks are not a substitute for that. That includes the first-run tray balloon, the HKCU value that records it, the `HTML source` label on the existing EDIT preview, Markdown display in RichEdit, SVG display in the image view (including a sharper raster after zoom, fit, or actual size settles, while pan still uses the bitmap already shown), PDF display in the image view (immediate shell icon, then the first page, including cancel and the password-protected and damaged fallbacks), the unsupported-file shell icon, center-anchored drag resize (`WM_ENTERSIZEMOVE` / `WM_SIZING`, minimum size, and the monitor work area), and Space-to-preview on the desktop (`Progman` / `WorkerW` host, `FindWindowSW(CSIDL_DESKTOP)`, follow-selection on the desktop list, cursor-monitor placement, and `LVM_GETSELECTEDCOUNT` on the desktop list view).
- Explorer, the taskbar, the notification area, and the preview window are meant to use the Spacepeek icon embedded in the executable, not the generic Windows application icon. The Win32 loader (`LoadIconWithScaleDown`) picks a size for the monitor DPI and reloads that size when the preview's DPI changes. That path is compile-checked, not run on a Windows desktop. The icon file's directory and the DPI size math are unit-tested.
